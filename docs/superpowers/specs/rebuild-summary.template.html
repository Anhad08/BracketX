01What the brief turned into

The ask was to make the UI work for beginners and experts alike. Reading the code first turned up something larger: ProgramBus held one program session, and take() replaced whatever was on air. A lower third and a ticker could not both be out.

That is a missing capability, not a layout. So the engine work went first and Production moved ahead of Design — capability takes longer to be wrong about.

A second finding sat alongside it: Depth — the beginner / expert split — had existed in the workspace since Phase 4 with no control anywhere in the UI. Both audiences were being denied the thing already built for them.

02The dock, before and after

The same screen, the same graphic, one click apart. On the left a beginner is asked for a name and a role. On the right everything is still reachable, closed until wanted.

Before this, Fill in showed all of it at once: Enable 3D, ten style chips, four lighting looks with exposure and shadows, five entrances — roughly thirty controls stacked above the one button that puts the graphic to air.

Two mechanisms rather than one, deliberately. At Fill in the advanced sections are absent; at Build they are present and closed. A disclosure somebody has to learn to ignore is still something they have to learn.

Unplanned consequence Collapsing those four sections made the layer tree visible at Build. It was always being rendered — thirty controls had pushed it below the fold. Part of “experts hit a ceiling” was a layout problem, not a missing feature.

03Two graphics, one output

ProgramBus now owns four named layers — background, lower, upper, overlay — each a full session with its own clock, built only when something is first taken to it. They composite in a fixed z-order.

Each verb — cue, take, cut, hold, continue, clear — names the layer it acts on. There is no default channel: a defaulting API is how everything quietly lands on one layer and the feature appears not to work.
