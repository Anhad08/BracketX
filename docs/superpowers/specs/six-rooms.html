The one finding worth arguing about

Press “Theme the stage too” while a light theme is loaded. The stage takes the theme's ground, and the lower third — which is white type on a translucent plate, designed to sit over video — becomes hard to read.

A broadcast graphic is judged against what it will actually composite over, and that is almost never a light surface. So --stage is a token a theme may set, but every light theme here deliberately keeps it dark. The chrome is the room; the stage is the picture.

Contrast is the exception and sets the stage to true black — an accessibility theme should maximise separation everywhere, including there.

How a theme is defined

Eleven values. No component knows a theme exists — everything reads tokens, which is why adding a seventh room is data rather than work. 

.studio[data-room="vision"] {
  --bg:        #0A0C14;   /* the ground behind everything */
  --chrome:    #131829;   /* rail and dock surface        */
  --chrome-2:  #1B2236;   /* raised within chrome         */
  --line:      #242C45;
  --line-2:    #38436A;
  --ink:       #EEF1F8;
  --ink-2:     #A8B2CC;
  --ink-3:     #7E88A6;
  --accent:    #7A6CF0;   /* the one interactive hue      */
  --accent-ink:#FFFFFF;
  --stage:     #06070D;   /* what the graphic is judged on */
}

What a theme may never change

On air is on air in every room. The semantic hues — air, cue, health — sit outside the theme and are only ever re-tuned for contrast against a light ground, never re-assigned. A tally that changed meaning with the wallpaper would be a defect, not a preference.

Still to decide

Whether themes are per operator or per installation. An editor makes it personal; a gallery with four positions may want every desk identical so anyone can sit at any of them. That is a product decision, not a design one — and it changes where the setting lives.
